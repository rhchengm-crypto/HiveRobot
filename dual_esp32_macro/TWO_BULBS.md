# 两灯控制：K8 / K9 / K4

## 当前映射

| 控件 | 目标 | 行为 |
|---|---|---|
| K8（副板GPIO23） | 新灯 second room c2；MAC d8:fc:92:e4:98:37；LAN IP 192.168.0.89 | 每次按下切换此灯开/关 |
| K9（副板GPIO32） | 原 Feit 灯泡 | 每次按下切换此灯开/关 |
| K4（副板GPIO26） | 上述两只灯 | 任一只开着则统一关；两只都关着则统一开 |
| 旋钮 | 原 Feit 灯泡 | 原有亮度控制，保持不变 |

只刷主板 macro_main，副板与接线均不变。长按不重复触发。

## 配置与运行

已通过当前Tuya项目验证新灯的 MAC，匹配 Device ID `REDACTED_LOCAL_DEVICE_ID`，确认在线并读取开关/功能定义。
新灯支持 switch_led，使用与原灯相同的云端HTTPS协议。新 Device ID 已加入本地 FeitSecrets.h，不需用户补填密钥。
控制仍走云端；MAC和局域网IP用于识别设备，不建立192.168.0.89的本地控制连接。
设备列表返回的ip是公网出口IP，不能用它与LAN IP做等值匹配；本次使用Tuya出厂信息MAC精确匹配。

两只灯独立保存状态，单灯失败不覆盖另一只的缓存。K4先确定一个统一目标，再顺序向两只灯发请求，因此实际亮灭可能略有先后。
如果某只灯状态未知且查询失败，K4取消本次总控，避免盲目反转；K8/K9仍可单独控制各自可用的灯。
K4发送过程中会尝试两只灯，即使第一只失败；出现部分失败时逐灯日志会明确显示，不能将组操作当成全部成功。
不因为部分失败自动反向回滚另一只灯，也不自动重发已发送但结果不明的控制请求。
缓存反映云端接受的目标/查询结果，不是物理光输出确认；外部App改状态后用串口status/status2重新同步。
屏幕 W 是WiFi，K9 是原灯状态，K8 是新灯状态，? 表示未知。

串口115200：
- 原灯：on / off / status
- 新灯：on2 / off2 / status2
- bright / temp / color 仍针对原灯。
- lcd 保留屏幕手动恢复。

## 上板验证

1. 只烧录主板，确认屏幕、九键、旋钮及副板冷启动正常。
2. 确认新旧灯都通电联网。日志 BULB1 为原灯，BULB2 为新灯。
3. 按K8两次，新灯应开/关，原灯不变；按K9两次，原灯应开/关，新灯不变。
4. 将两灯都关，再按K4：两灯都开；再按K4：两灯都关。
5. 单独打开任一灯，再按K4：两灯统一关闭；测试两种混合状态。
6. 调旋钮，确认只改变原灯亮度。
7. 测试一只离线时另一只单控可用，并核对K4逐灯结果，避免把部分成功当作全部成功。

本次已完成云端MAC匹配和状态/功能只读查询，以及编译期总控逻辑测试；代码编译结果见BUILD_RESULTS。
未刷板，也未通过本次代码实际验证两灯亮灭。云端发现时原灯标记离线，新灯在线；上板测试前需确认原灯已联网。
