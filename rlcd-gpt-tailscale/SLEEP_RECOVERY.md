# RX 休眠唤醒稳定性修正（2026-11-06）

现象：用户反馈长时间休眠后，接 RX 的按键无法恢复屏幕。曾黑屏且 USB 串口不可见；拔 USB 后用真正的板载 PWR 关机/开机，再接 USB 可恢复。恢复后测得电池 4.131V、估算 97%，麦克风、SD 和网络正常。故障前的电压与内部执行位置没有记录，不能据此确定根因或排除先前的供电问题。

用户后续明确：短时间休眠可用 RX 正常唤醒，整夜休眠后不行。旧固件恢复后读到 count=1、result=0、reason=7（GPIO）、mic=1。短时测试不能作为整夜故障已复现或修复的证据。

修正：
- 保留轻睡眠与 GPIO44 按键唤醒，关闭 CONFIG_PM_POWER_DOWN_CPU_IN_LIGHT_SLEEP，避免 CPU 断电与缓存上下文恢复路径。并非改成深睡眠，也并非仅关闭屏幕。此选项关闭后休眠电流可能略升，未实测增量。
- 每次休眠前重新设置 GPIO44 输入上拉并检查唤醒 API 返回值；失败时保留屏幕并显示错误。
- 唤醒后完整初始化 ST7305、重画原页面，再恢复 USB、麦克风和 Wi-Fi；避免后续步骤延迟时一直显示空白。
- 正常休眠没有定时自动亮屏。sleep-test 仅用于 3 秒自动唤醒测试；sleep-long 仅用于 120 秒自动唤醒测试。两者都同时保留 RX 按键唤醒。
- sleep-info 增加休眠时长、恢复耗时、CPU 断电配置和 RX 电平，分阶段打印恢复日志。

工程迁移到桌面 esp32/rlcd-gpt-tailscale 后，原 build 缓存仍引用旧路径；新版本使用 build-sleep-recovery 目录独立构建，原构建目录保留。build.ps1 新增 -BuildDir 参数，默认使用 build-sleep-recovery。

验证状态：完整编译和最终固件重编译通过；仅刷入 app（0x10000），MAC 28:84:85:a8:8f:70，写入哈希校验通过，未擦除 NVS/分区/SD。两分钟自动唤醒通过：实际休眠 119999ms，恢复 310ms，CPU 断电关闭；唤醒后 ES7210 实际读取 32000 帧成功，SD 和 Wi-Fi 正常。首次诊断脚本的 4 秒麦克风等待过短，下一次读取已收到成功结果，脚本改为 10 秒等待。实体 RX 连续三次唤醒通过，用户确认“三次都正常恢复”；计数为 4（一次定时+三次 GPIO），最近一次 GPIO 唤醒 reason=7、恢复 311ms，随后麦克风再次读取 32000 帧成功；尚未验证整夜休眠，不能宣称整夜问题已解决。


## 与 9 键灯控版的对比

9 键版 macro_main/macro_main.ino:35 的 screenOff 只执行背光关闭和动画隐藏；ScreenIdle.h:3 明确是 display-only。loop 始终执行 keys.service，触摸、网络任务继续运行，未调用 ESP32 轻/深睡眠接口。唤醒时重画界面再开背光。

RLCD firmware/main.cpp:508 的 sleepDevice 调用 esp_light_sleep_start，退出 VPN、暂停音频、关闭 Wi-Fi 和 USB 通信，需要 GPIO44 硬件唤醒并恢复外设。本版仍是轻睡眠，只关闭 CPU 域断电选项并强化恢复顺序。因此 9 键整夜正常不等于这条芯片唤醒路径已经验证正常。

可另做类似 9 键的息屏待机，保持主控运行以绕过芯片唤醒路径，但通常会增加待机耗电。当前没有改成该模式，也没有修改或刷写 9 键主板。整夜效果待用户留机验证。
